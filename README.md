
## Прогноз погоды
`GET /api/equipment/:id/weather` запрашивает ежедневный прогноз из Open-Meteo, используя координаты оборудования. День считается подходящим для работы на открытом воздухе, если осадки ниже `WEATHER_MAX_PRECIPITATION`, а максимальная скорость ветра ниже `WEATHER_MAX_WIND_SPEED_KMH`.
Интеграция с погодой настраивается следующими переменными:
- `WEATHER_API_URL` - URL API прогноза;
- `REQUEST_TIMEOUT_MS` - таймаут внешнего запроса;
- `WEATHER_FORECAST_DAYS` - количество дней прогноза;
- `WEATHER_MAX_PRECIPITATION` - максимально допустимое количество осадков;
- `WEATHER_MAX_WIND_SPEED_KMH` - максимально допустимая скорость ветра.
Если оборудование не существует, эндпоинт возвращает `404`. Если внешний погодный сервис недоступен или возвращает невалидные данные, эндпоинт возвращает `502` с сообщением об ошибке; процесс приложения продолжает работать.

В development-режиме для диагностики в ответ также добавляется поле `stack`.
В production-режиме внутренние ошибки (включая ошибки внешних сервисов) возвращают
нейтральное сообщение без стека и внутренних деталей; подробности доступны в логах
по `requestId`.

# Задание
# 1. Условие

Требуется разработать **REST API на Express** для учёта заявок на техническое обслуживание оборудования производственной площадки (например, ветропарка). Сервис ведёт справочник оборудования и заявки на его обслуживание, контролирует жизненный цикл заявки и позволяет оценить погодные условия на объекте перед планированием наружных работ.

Данные на этой неделе хранятся в **JSON-файле или в памяти процесса** - база данных подключается на Неделе 3. Доступ к данным выполняется **только через слой репозитория**, чтобы последующая замена хранилища не затрагивала остальной код.

---

## 2. Модель данных

### Оборудование (equipment)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | string | uuid, генерируется сервером |
| `name` | string | 3–100 символов, обязательное |
| `type` | string | `turbine` \| `inverter` \| `sensor` \| `substation` |
| `serialNumber` | string | уникальный в пределах системы |
| `location` | object | `{ lat: number, lon: number }` |
| `status` | string | `operational` \| `maintenance` \| `fault` \| `decommissioned` |
| `installedAt` | string | ISO-дата, не в будущем |

### Заявка на обслуживание (maintenance request)

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | string | uuid, генерируется сервером |
| `equipmentId` | string | ссылка на существующее оборудование |
| `title` | string | 5–120 символов, обязательное |
| `description` | string | до 2000 символов |
| `priority` | string | `low` \| `medium` \| `high` \| `critical` |
| `status` | string | `new` \| `in_progress` \| `done` \| `rejected` (по умолчанию `new`) |
| `plannedAt` | string | ISO-дата-время, необязательное |
| `createdAt` | string | ISO-дата-время (проставляется сервером) |
| `updatedAt` | string | ISO-дата-время (проставляется сервером) |

### Допустимые переходы статуса заявки

```
new → in_progress → done
new → rejected
in_progress → rejected
```

Из статусов `done` и `rejected` переходы **запрещены**. Попытка недопустимого перехода - ответ **409**.

## 3. Состав API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Проверка доступности сервиса |
| GET | `/api/equipment` | Список оборудования: фильтры, сортировка, пагинация |
| POST | `/api/equipment` | Создание единицы оборудования |
| GET | `/api/equipment/:id` | Карточка оборудования |
| PATCH | `/api/equipment/:id` | Частичное обновление |
| DELETE | `/api/equipment/:id` | Удаление (запрещено при наличии открытых заявок) |
| GET | `/api/equipment/:id/requests` | Заявки по конкретной единице оборудования |
| GET | `/api/equipment/:id/weather` | Прогноз по координатам объекта и пригодность окна для наружных работ |
| GET | `/api/requests` | Список заявок: фильтры, сортировка, пагинация |
| POST | `/api/requests` | Создание заявки |
| GET | `/api/requests/:id` | Карточка заявки |
| PATCH | `/api/requests/:id` | Редактирование полей заявки |
| PATCH | `/api/requests/:id/status` | Смена статуса заявки с проверкой допустимости перехода |
| DELETE | `/api/requests/:id` | Удаление заявки |

**Требования к эндпоинту прогноза:** сервис берёт координаты оборудования, обращается к внешнему погодному API (модуль из Кейса 1) и возвращает прогноз вместе с признаком пригодности окна для наружных работ. Правило пригодности задаётся в конфигурации (например, отсутствие осадков и скорость ветра ниже порога) и описывается в README.

Ошибка или недоступность внешнего API **не должна приводить к падению сервиса**: возвращается корректный код ответа и понятное сообщение.

## 4. Функциональные требования

1. Списочные эндпоинты поддерживают фильтрацию (по статусу, типу, приоритету, идентификатору оборудования, диапазону дат), сортировку и пагинацию. Ответ содержит данные и метаданные: `total`, `page`, `limit`.

2. Создание заявки на несуществующее оборудование отклоняется с кодом **404**, создание оборудования с уже занятым серийным номером - с кодом **409**.

3. Удаление оборудования, по которому есть незакрытые заявки, запрещено (**409**).

4. Изменение статуса выполняется отдельным эндпоинтом и проверяется по таблице допустимых переходов.

5. Поля `id`, `createdAt` и `updatedAt` проставляются сервером и не могут быть изменены через API. Неизвестные поля тела запроса игнорируются.

6. Все ответы об ошибках имеют единый формат, например:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [
      { "field": "priority", "message": "Недопустимое значение" }
    ],
    "requestId": "b1f2c3d4"
  }
}
```

## 5. Технические требования

### Архитектура

- Слоистая структура: **маршруты → контроллеры → сервисы → репозитории**.
- Бизнес-логика в сервисах, работа с данными - только в репозиториях.
- Пример структуры:
  ```
  src/app.js
  src/server.js
  src/routes/
  src/controllers/
  src/services/
  src/repositories/
  src/middlewares/
  src/validators/
  src/errors/
  src/config/
  ```
- Сборка приложения отделена от запуска сервера: модуль `app` экспортируется и может быть подключён в тестах.
- Конфигурация - только через переменные окружения (`PORT`, `NODE_ENV`, `CORS_ORIGINS`, `RATE_LIMIT_*`, `WEATHER_API_URL`, `REQUEST_TIMEOUT_MS`). В репозитории - `.env.example`.

### Middleware и обработка ошибок

- Логирование запросов, разбор JSON с ограничением размера, присвоение идентификатора запросу, валидация, обработчик 404, централизованный обработчик ошибок - **в указанном порядке**.
- Валидация выполняется отдельным переиспользуемым middleware (собственная реализация или библиотека уровня Joi / Zod / express-validator) и покрывает `body`, `params` и `query`.
- Ошибки приложения описаны собственными типами (`NotFoundError`, `ValidationError`, `ConflictError`) и преобразуются в HTTP-ответ только в обработчике ошибок.
- Асинхронные ошибки контроллеров передаются в обработчик ошибок, необработанных отклонений промисов нет.
- В режиме `production` в ответ не попадают стек-трейсы и внутренние сообщения.

### Безопасность

- **CORS:** явный список разрешённых источников из переменной окружения, а не «`*`». В README поясняется, какие источники и почему разрешены.
- Ограничение частоты запросов на маршруты `/api` с ответом **429** и заголовками лимита.
- Ограничение размера тела запроса и защитные HTTP-заголовки (helmet или ручная настройка).
- Если в решении используются cookie - флаги `HttpOnly`, `Secure`, `SameSite` выставлены осознанно, выбор значения `SameSite` поясняется.

### Логирование

- Каждый запрос логируется: **метод, путь, код ответа, длительность, идентификатор запроса**.
- Ошибки логируются с идентификатором запроса, который возвращается клиенту и позволяет найти запись в логах.
- Используются уровни логирования; отладочные вызовы `console.log` в итоговом коде **отсутствуют**.
